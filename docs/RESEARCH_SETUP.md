# RainyDay Café classroom research, 28 October 2026

## Authorised study setup

One fixed condition per participant for the classroom session. Conditions are balanced randomly within the session by the server, including participants who subsequently stop. Both groups select a card and confirm the intervention. The prediction group sees the seven scored indicators, predicted score and programmed observation before commitment. The control group sees these consequences after commitment. No live AI is involved. Existing rules, cards, artwork and win thresholds are preserved.

Repeated runs are linked by a random participant credential scoped to `rd-2026-10-28`. No names, emails, student IDs, IP addresses, browser fingerprints, referring URLs or free text are stored in the research database. The eight-character code is a display reference, not an authentication credential. Codes and participant credentials must not be used across later classroom sessions. Server enrolment closes at 00:00 UTC on 29 October. Existing queued records can still upload afterwards. Browser storage is used to survive reloads and interrupted uploads. A reload begins a new run, retaining the earlier attempt as incomplete. It does not resume the earlier game state.

The study notice is optional, makes no claim of university ethics approval, and allows the ordinary game without research recording. Participation is unrelated to marks. Initial team diagnoses and explanations are not recorded. There are no new written prediction/reflection questions. Interviews remain retrospective explorations of participants' perspectives. Ethical approval and institutional retention requirements are not established by software implementation.

## Tomorrow's operation

1. Students open https://rd-cafe.sbond.uk/ and read the classroom research information. Those who agree select **Take part and continue**, then **Start Simulation**. Others select **Play without recording**.
2. Students play individually and repeat **Play Again** during the allotted 45–60 minutes. Each retains the same version and study code. Avoid sharing predicted consequences between the two groups until gameplay finishes. Conduct the usual common tutor debrief afterwards.
3. Ask interview volunteers to retain their displayed study code, for example by writing it down. Keep any interview identity mapping separate from the gameplay exports. Do not collect names through the game.
4. **Records saved** confirms server acknowledgement of the current queue. **Saving…** means a queue remains. An error message means the records are retained locally for retry: keep the tab open and restore connectivity. Do not clear browser storage. Abrupt exits can lose final visibility events; absence of an exit event is not evidence of continued play.
5. A student can use **Study controls** to stop further recording while retaining saved records, or delete their records. For shared devices use a separate browser profile/private browsing session for each person. Browser storage identifies the session's code, not the human operating a shared device. Ordinary duplicate tabs share the participant code but start independent run IDs.
6. Open https://rd-cafe.sbond.uk/research and enter the access key from the separately supplied private access file. The key is never embedded in the build, URL, export or browser storage. Lock the records before sharing the screen.
7. Download **full JSON** (all events and canonical state/feedback), **decisions CSV** (one row per committed turn), and **events CSV**. Use the code filter and run selector for replay. Participant records and test data are separated. A completed run means the final summary was displayed; `decisions_complete` means all seven decisions were made but the summary was not observed. `incomplete` means fewer decisions and no recorded restart; `restarted` is an explicitly superseded partial attempt.
8. The researcher can delete a participant using the code-filtered table, including after the student has stopped recording. Deletion removes gameplay from the primary database and available server backups; only a credential tombstone remains to block late uploads. Previously downloaded exports/interview mappings are outside the app and require separate handling.

## Data and interpretation

Every event has an immutable UUID, participant/run/page references, per-page sequence, browser elapsed time, client clock time, server receipt time, release version, event type and allowlisted data. The server validates the intervention sequence and reconstructs state using the same bundled rules. No client-supplied raw prose is accepted. Batches are atomic and duplicate retries are idempotent. Duplicate IDs with conflicting content, other participants' runs, missing turn sequences and incompatible releases are rejected rather than silently recorded.

Events cover run starts/restarts, card and section visibility, category toggles, selection/cancellation, predictions actually opened, commitments, result display/dismissal, summary display, metric breakdowns, node tooltips, case collapse/expansion, mobile tabs, page visibility/exit, and visible animation counters sampled every ten seconds. Geometry-based visibility means an area was on screen, not that it was read or attended to. Timing uses each page's elapsed clock; use page IDs and sequence for ordering across reloads. Server timestamps record upload timing, which can lag play during disconnection.

Canonical state includes raw and displayed metrics, flags, score, metric contributions, complete intervention sequence, all turn observations and final outcome. The seven scored metrics include Waste Control; throughput is internal and appears in per-turn results but is not part of the overall average. The seventh observation must be acknowledged before the final summary. Identical sets yield identical final rule-based indicators regardless of order; intermediate states and feedback can differ. Customer animation includes randomness and is not an exact film of the decision state. Replay reconstructs recorded rules, decisions and text, not identical customer movement. Improved scores alone do not establish explanation development or learning gains. Multiple runs from one student are linked observations, not independent participants.

## Hosting, access and preservation

A dedicated Node 22 service uses built-in SQLite. Caddy forwards only `/api/research/*` to it; static game routes remain separate. The database is bind-mounted at `/home/ubuntu/apps/rd-cafe/research-data`, outside static `/srv`, with restrictive permissions. The service records startup/backup-failure notices but no request access logs. Researcher endpoints require a separately generated bearer key. Participant credentials are stored as hashes on the server. Fonts are self-hosted to avoid third-party font requests.

Consistent SQLite snapshots are made at startup, hourly, and on researcher request or participation-ending actions, in `research-data/backups`. They are on the same VPS, not off-site backups. No automatic research-data deletion date is invented; the institution's retention decision remains to be applied. Docker-image cleanup never touches the database, backups, access key or other applications.

Production builds start from the committed deployed game and overlay only this research change. The pre-existing local 3D experiment and other uncommitted work are excluded from production and preserved locally. Build output has a SHA-256 manifest and release identifier. The service rejects events from a different release, avoiding silent mixtures of rule/content versions.
